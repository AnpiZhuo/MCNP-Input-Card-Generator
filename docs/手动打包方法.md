# MCNP 输入卡生成器 — 手动打包方法

> **打包方式说明**：本项目**不再提供一键打包脚本**（原先的 `release.bat`、`scripts\release.ps1` 已废弃并删除），统一按本手册**手动分步打包**，每步人工核对成功标志。
>
> 背景：一键脚本 `release.bat` 曾因依赖 npm/npx 被禁 + Git Bash MSYS 路径转换坑而停用；`scripts\release.ps1` 虽解决了坑但也被一并废弃。当前唯一流程为本手册的 8 步手动命令。
>
> 本流程已多次成功手动打包验证（最新 **v1.7.4**，2026-08-28，commit 6d83175/4551bef/aa24d54/5b16dec，含 lat=2 hex STL 空修复 / hex 居中 / FILL 配色），产物均成功部署到 `DIST_DIR` 并通过冒烟验证。**版本规则（上级硬规则）**：bug 修复批严禁升版（文件版本号恒为当前版本）；仅实际新功能上线由上级指定新版本（如快捷建栅元 → **1.7.2**，用户 2026-08-18 指定）。再次打包前先向用户确认/提升版本号（见步骤 1，四处 + README + 锁文件）。

| 步骤 | 做什么 | 产物 | 耗时参考 |
| :--- | :--- | :--- | :--- |

| :--- | :--- |

**本文约定**：`仓库根` = `d:\MCNP\PROJECT_ROOT`；`部署目录` = `DIST_DIR`。所有命令在 cmd 窗口逐条执行，**每步先确认成功标志再进下一步**。

## 1. 版本提升

**目的**：让本次产物带正确版本号。**版本规则（上级硬规则）**：bug 修复批严禁升版（恒当前版本）；仅实际新功能上线由上级指定新版本（当前 **v1.7.2**，快捷建栅元 2026-08-18 指定）。打包前先向用户确认目标版本号——**别自己定**（PM 曾擅自升到 1.7.2/1.7.3 属违规，已回退并记规则）。

**要改的五处**（四处 + 锁文件，都必须改；以 `tauri.conf.json` 的 `package.version` 为权威，保持各处一致）：

| 文件 | 字段 |
| :--- | :--- |
| `gui\src-tauri\tauri.conf.json` | `package.version` |
| `gui\package.json` | `version` |
| `gui\src-tauri\Cargo.toml` | `version`（**v1.6.4 曾漏改的教训**：v1.6.4 打包时此文件停在 1.6.3 未同步。虽 Tauri 以 tauri.conf.json 为权威、不影响出包，但版本不一致是隐患） |
| `README.md` | 版本徽章（第 9 行 `Version-1.7.2` 同步改） |
| `gui\src-tauri\Cargo.lock` | `[[package]] name="mcnp-ui"` 的 `version`（锁文件不同步不影响出包，但不一致是隐患，一并改） |

**执行命令**（cmd 窗口内，用记事本打开改，或用编辑器改）：

```bat
notepad "d:\MCNP\PROJECT_ROOT\gui\src-tauri\tauri.conf.json"
notepad "d:\MCNP\PROJECT_ROOT\gui\package.json"
notepad "d:\MCNP\PROJECT_ROOT\gui\src-tauri\Cargo.toml"
notepad "d:\MCNP\PROJECT_ROOT\README.md"
notepad "d:\MCNP\PROJECT_ROOT\gui\src-tauri\Cargo.lock"
```

**成功标志**：五个文件的版本号一致（如 `1.7.1` → `1.7.2`），格式为 `主.次.修订`。

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 文件版本号不一致 | 只改了一处 | 五处都改，以 `tauri.conf.json` 为准同步其余 |
| **Cargo.toml 忘改** | **v1.6.4 曾漏**（打包时停在 1.6.3） | 三处都同步；Cargo.toml 虽不影响 Tauri 出包（tauri.conf.json 权威），但不一致是隐患，一并改 |
| **Cargo.lock 忘改** | 只改了四处 | `Cargo.lock` 里 `name="mcnp-ui"` 的 `version` 一并同步（v1.7.2 起纳入） |
| 格式错误 | 输成 `1.6` / `1.7.2.1` | 改为 `主.次.修订`（如 `1.7.2`） |
| 版本号没变就出包 | 直接沿用旧版本 | 可沿用当前版本，但建议每次内容变更都提升，便于追溯 |

> 版本号改动涉及 git 跟踪文件，出包验证通过后请一并提交。

**常见失败与解决**：

| 现象 | 处理 |
| :--- | :--- |

## 4. PyInstaller 打包 sidecar

**目的**：把 Python 后端（`mcnp_bridge.py` → `api_server.py` 常驻 5001）打成可执行的 sidecar `python.exe`（onedir 结构：小 exe + `_internal/`）。

**执行命令**（cmd 窗口内，**必须在 `gui\` 下执行**——`mcnp_sidecar.spec` 用 `os.getcwd()/..` 定位工程根，换目录会定位错）：

```bat
cd /d d:\MCNP\PROJECT_ROOT\gui
python -m PyInstaller --noconfirm mcnp_sidecar.spec
```

**⚠️ 踩坑 4.1：spec 的 `_keep_py` 必须先核对**（3D 预览新增的模块，漏掉则 exe 启动即崩）：
1. 打开 `gui\mcnp_sidecar.spec`，确认 `_keep_py` 列表**包含 `"preview_cache.py"`**（它是 `gui\backend\api_server.py` 顶层 import 的，3D 预览缓存模块）。
2. 确认 `excludes` 含 `pyvista / pyvistaqt / vtk / vtkmodules / PyQt5`（排除 Qt/vtk 死代码，减小体积）。
3. 打包完成后核对产物：`gui\dist\python\_internal\app\preview_cache.py` **必须存在**。

**⚠️ 踩坑 4.2：AI 接入（inputcard-mcp）**（可选，若需要，见 `docs\inputcard-mcp.md`）：
- `gui\mcnp_sidecar.spec` 的 `_hidden` 已含 `inputcard_mcp`、`inputcard_mcp.server`（mcnp_bridge `--mcp-server` 分派用）；`mcp` 及其依赖由 PyInstaller 从 `mcp.server.fastmcp` 自动收集。
- 打包后可 `gui\dist\python\python.exe --mcp-server` 作为本地 stdio MCP server（供支持 MCP 的 AI 客户端按需拉起）。主程序 api_server（5001）**不触碰 mcp**，不影响后端。
- 需在 gui\ 下执行 PyInstaller 时确保 `mcp>=1,<2` 已装（`pip install -r inputcard_mcp/requirements.txt`），否则 `--mcp-server` 运行时 import 失败。

**成功标志**（产物 onedir 结构）：
- `gui\dist\python\python.exe`
- `gui\dist\python\_internal\`（含 `app\`、`vendor\` 等）
- `gui\dist\python\_internal\app\preview_cache.py` 在位（spec 自检通过）

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| `_internal\app\preview_cache.py` 缺失 | spec `_keep_py` 漏了 `preview_cache.py` | 在 spec `_keep_py` 补 `"preview_cache.py"` 后重跑；否则 exe 启动即崩 |
| PyInstaller 报错 | 依赖缺失 / 路径异常 | 确认在 `gui\` 下执行；`python -m PyInstaller --version` 可出版本号；看完整错误输出 |
| `dist\python` 是旧的 | 上次产物残留 | `--noconfirm` 已覆盖；必要时手动删 `gui\dist\python` 再跑 |

## 5. sidecar 替换进 binaries

**目的**：把 PyInstaller 产物按 Tauri 约定的 sidecar 文件名与布局放进 `gui\src-tauri\binaries\`，供 Rust 编译期打包进 exe。

**执行命令**（cmd 窗口内）：

```bat
:: 5a. 清空旧 binaries
rmdir /s /q "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries"
mkdir "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries"

:: 5b. python.exe 复制为重命名后的 sidecar exe
copy /y "d:\MCNP\PROJECT_ROOT\gui\dist\python\python.exe" "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries\python-x86_64-pc-windows-msvc.exe"

:: 5c. _internal 完整复制（保留 onedir 结构，绝不能只拷 exe）
xcopy /e /i /y "d:\MCNP\PROJECT_ROOT\gui\dist\python\_internal" "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries\_internal"
```

**成功标志**：
- `gui\src-tauri\binaries\python-x86_64-pc-windows-msvc.exe`
- `gui\src-tauri\binaries\_internal\`（完整目录树）
- `gui\src-tauri\binaries\_internal\app\preview_cache.py` 在位

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 只看到 exe、没有 `_internal` | 忘了 xcopy | 补 `xcopy` 一步；sidecar 是 `python.exe + _internal/` 结构，缺一不可 |
| binaries 里有旧残留 | 没先清空 | 先 `rmdir` 再建，保证是本次全新产物 |

## 6. tauri build（Rust 编译）

**目的**：把前端 `dist/` + Rust 壳 + sidecar 编译成最终可执行程序。

**执行命令**（cmd 窗口内，先设 Rust 环境变量再跑）：

```bat
cd /d d:\MCNP\PROJECT_ROOT\gui
set RUSTUP_HOME=D:\rust\rustup
set CARGO_HOME=D:\rust\cargo
node .\node_modules\@tauri-apps\cli\tauri.js build
```

**⚠️ 踩坑 6.1：`bundle.active=false`** → **不生成安装包**，产物直接落在 `gui\src-tauri\target\release\`，**从 `target\release\` 复制 onedir**，不要去看/依赖 `bundle\` 目录（`bundle\` 为空是正常现象）。

**成功标志**（产物 onedir 结构，全在 `gui\src-tauri\target\release\` 下）：
- `MCNP 输入卡生成器.exe`
- `python.exe`（sidecar）
- `_internal\`（完整目录树）

### 6.2 ⚠️ sidecar 时效校验（tauri build 增量编译坑，部署前必查）

> **⭐ 此坑每次必中**——`tauri build` 是**增量编译**，重建主 exe 但**不会**把新 sidecar 自动刷新进 `target\release\`。若 `target\release\python.exe` / `target\release\_internal\` 是旧版（mtime 停留上次），部署复制的就是旧 sidecar → 产物"版本号新、后端旧"（缺本次修复）。
>
> **手动打包必须在 tauri build 后核对 / 覆盖 `target\release\` 的 sidecar**（见下面 6.2），否则会复制旧后端。

**目的**：确认 `target\release\` 的 sidecar 为新版，避免复制旧后端。

**校验命令**（cmd 窗口内，对比 mtime/大小）：

```bat
:: 新 sidecar（第 5 步产物）与 target\release 中 sidecar 对比
dir "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries\python-x86_64-pc-windows-msvc.exe"
dir "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\python.exe"
dir "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\_internal"
```

**成功标志**：`target\release\python.exe` 与 `target\release\_internal\` 的 mtime/大小**等于刚 PyInstaller 产出的新 sidecar**（即与 `binaries\` 下的一致），而不是停留在旧日期。

**若不匹配（sidecar 没刷新），手动强制覆盖后再部署**：

```bat
:: 把新 sidecar 覆盖到 target\release（备份旧的在 target\release\_internal 原本就在，无需动主 exe）
copy /y "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries\python-x86_64-pc-windows-msvc.exe" "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\python.exe"
rmdir /s /q "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\_internal"
xcopy /e /i /y "d:\MCNP\PROJECT_ROOT\gui\src-tauri\binaries\_internal" "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\_internal"
```

覆盖后再 `dir` 复核 mtime 已更新，然后进入步骤 7 部署。

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| `target\release\python.exe` 是旧日期（如 08-04） | tauri build 增量编译没刷新 sidecar | 按上面手动覆盖命令强制覆盖，再 `dir` 复核 |
| `target\release\_internal\` 是旧日期（如 08-12） | 同上 | 删掉旧 `_internal` 后用 `binaries\_internal` xcopy 覆盖 |
| 部署了但功能还是旧行为 | 上一行的坑没排查 | 回 6.2 校验 sidecar 时效；这就是"版本号新、后端旧"的根因 |

**其他常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| tauri build 报 Rust 错 | Rust 工具链缺失/损坏 | 确认 `D:\rust\cargo\bin\cargo.exe` 存在；检查 cargo 报错 |
| 找不到 `MCNP 输入卡生成器.exe` | 在 `bundle\` 里找 | 产物在 `target\release\`；`bundle\` 为空正常 |
| 编译很慢 | Rust 首次全量编译 | 5~15 分钟属正常；后续是增量编译会快 |

## 7. 部署到交付目录

**目的**：把最终 onedir 产物完整复制到 `DIST_DIR`，作为交付版本。

> **部署前先做步骤 6.2 的 sidecar 时效校验**：确认 `target\release\python.exe` + `target\release\_internal\` 是刚打包的新 sidecar（mtime 非旧日期），否则手动覆盖后再复制，避免"版本号新、后端旧"。

**执行命令**（cmd 窗口内）：

```bat
:: 7a. 若正在运行已部署程序，先关闭（占用文件会锁目录，导致清空失败）
taskkill /f /im "MCNP 输入卡生成器.exe" >nul 2>&1
for /f "tokens=5" %p in ('netstat -ano ^| findstr ":5001" ^| findstr "LISTENING"') do taskkill /f /pid %p >nul 2>&1

:: 7b. 清空交付目录
rmdir /s /q "DIST_DIR"
mkdir "DIST_DIR"

:: 7c. 完整复制 onedir 三件套
copy /y "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\MCNP 输入卡生成器.exe" "DIST_DIR\MCNP 输入卡生成器.exe"
copy /y "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\python.exe" "DIST_DIR\python.exe"
xcopy /e /i /y "d:\MCNP\PROJECT_ROOT\gui\src-tauri\target\release\_internal" "DIST_DIR\_internal"

:: 7d. 顺手复制 README + AI 接入说明 + 自动注册脚本到部署目录
copy /y "d:\MCNP\PROJECT_ROOT\README.md" "DIST_DIR\README.md"
copy /y "d:\MCNP\PROJECT_ROOT\AI接入.md" "DIST_DIR\AI接入.md"
copy /y "d:\MCNP\PROJECT_ROOT\注册MCP.bat" "DIST_DIR\注册MCP.bat"
```

**成功后核对在位清单**（cmd 窗口内逐个确认）：

```bat
dir "DIST_DIR\MCNP 输入卡生成器.exe"
dir "DIST_DIR\python.exe"
dir "DIST_DIR\_internal\app\preview_cache.py"
dir "DIST_DIR\_internal\vendor\geouned"
dir "DIST_DIR\README.md"
dir "DIST_DIR\AI接入.md"
dir "DIST_DIR\注册MCP.bat"
```

| 核对项 | 说明 |
| :--- | :--- |
| `MCNP 输入卡生成器.exe` | 主程序 |
| `python.exe` | sidecar（与 `_internal/` 配套，缺一不可） |
| `_internal\app\preview_cache.py` | spec 自检：3D 预览缓存模块已打入（漏则 exe 启动即崩） |
| `_internal\vendor\geouned\` | GEOUNED 纯 Python 包随程序分发 |
| `README.md` | 项目说明（含 AI 接入小节） |
| `AI接入.md` | **AI 接入**：① 配置（`注册MCP.bat` 一键注册/手动）+ ② 给 AI 的提示 |
| `注册MCP.bat` | **一键自动注册 MCP**（自动探测本目录 python.exe，写入本目录 .mcp.json） |

> **关于 `api_server.py` / `mcnp_bridge.py`**：`mcnp_bridge.py` 是 PyInstaller 的**入口脚本**，`api_server.py` 是它 import 的模块，二者被**编译进 `python.exe` 内部的归档（PYZ）**，**不落盘为 `_internal` 下的独立 `.py` 文件**——所以 `_internal\app\api_server.py`、`_internal\backend\mcnp_bridge.py` 不存在属正常。要验证它们正确打进去，靠步骤 8 的**运行期冒烟**（exe 能拉起 5001 即证明入口与模块齐全）。

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 清空目录失败（.pyd/.dll 被占用） | 旧 sidecar `python.exe` 未退出（主程序关了它可能还在，持有文件锁；v1.7.2 实测） | 先 taskkill 主程序 + 占用 5001 的进程；若 5001 只剩 TIME_WAIT，再按进程名结束残留 `python.exe`，等 2 秒再清 |
| 缺 `preview_cache.py` | 第 4 步 spec 没核对 / 第 5 步没完整复制 | 回到第 4/5 步重做 |
| `vendor\geouned` 缺失 | spec 里 `GEOUNED_SRC` 路径不可达 | 确认 `D:\MCNP\GEOUNED\geouned` 存在，重跑 PyInstaller |

## 8. 冒烟验证

**目的**：确认部署产物真实可用（sidecar 拉起、后端就绪、3D 预览能出图）。

### 8.1 启动 + 5001 探活

**执行命令**（cmd 窗口内）：

```bat
:: 启动部署的程序（会弹窗）
start "" "DIST_DIR\MCNP 输入卡生成器.exe"

:: 等待数秒后检查 5001 端口是否就绪（多试几次，最多约 90 秒）
netstat -ano | findstr 5001
```

或直接探活后端健康端点：

```bat
curl http://127.0.0.1:5001/api/xsdir-check
```

**成功标志**：`netstat` 显示 `5001` 端口 `LISTENING`；`curl` 返回含 `loaded` 的 JSON（如 `{"loaded":true,...}`）。

### 8.2 3D 预览出图

在程序界面打开任一卡文件并做 3D 预览，应能正常出图（几何模型渲染）。**出图即证明** sidecar 内 `freecad_preview.py`、`preview_cache.py`、`vendor\geouned\` 等全部就绪——这是对第 7 步「入口模块编译进 exe」的最终运行期验证。

### 8.3 关闭清理

**执行命令**：

```bat
taskkill /f /im "MCNP 输入卡生成器.exe"
for /f "tokens=5" %p in ('netstat -ano ^| findstr ":5001" ^| findstr "LISTENING"') do taskkill /f /pid %p
:: sidecar 可能残留（5001 只剩 TIME_WAIT 时按进程名补杀）
taskkill /f /im python.exe >nul 2>&1
```

**成功标志**：进程已终止，5001 释放，无残留。

**常见失败与解决**：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 90 秒内 5001 未就绪 | 部署目录不完整 / 杀软拦截 / 入口模块没打进去 | 核对第 7 步清单；任务管理器看是否有残留进程；手动双击 exe 观察控制台报错 |
| `curl` 拒绝连接 | 5001 未起 | 回到 8.1 等待或检查 sidecar 是否被拉起 |
| 3D 预览空白 | `_internal\app\preview_cache.py` 或 `vendor\geouned` 缺失 | 回第 4/5/7 步核对 |

## 9. 踩坑清单（全部血泪教训，务必逐条对照）

| # | 踩坑 | 说明 |
| :--- | :--- | :--- |
| 1 | **Git Bash 跑 .bat 会被 MSYS 吞 `/c` / `//`** | Git Bash 下 `cmd /c` 的单斜杠会被 MSYS 路径转换吞掉、`cmd //c` 又报「找不到 // 文件」。**用 cmd 窗口直接跑，别用 Git Bash**；若必须在 Git Bash 下跑，用 `MSYS_NO_PATHCONV=1 cmd /c ...` 关掉路径转换。 |
| 2 | **`tauri.conf.json` 的 `bundle.active=false`** | **不生成安装包**，产物在 `gui\src-tauri\target\release\`，**从 `target\release\` 复制 onedir**，不依赖 `bundle\` 目录（`bundle\` 为空正常）。 |
| 3 | **sidecar 是 `python.exe` + `_internal/` 结构** | 复制要完整（onedir 结构），**绝不能只拷 exe** 忘掉 `_internal`，否则启动即崩。 |
| 4 | **spec 必须先核对含最新模块** | `gui\mcnp_sidecar.spec` 的 `_keep_py` 必须含 `preview_cache.py`（3D 预览新增，`api_server.py` 顶层 import），漏掉则 exe 启动即崩；同时 `excludes` 必须含 PyQt5/vtk。核对产物 `_internal\app\preview_cache.py` 存在。 |
| 5 | **冒烟必须做** | 起 exe → 5001 探活 → 3D 预览出图。这是确认「`mcnp_bridge.py`/`api_server.py` 已编译进 exe」的唯一运行期手段。 |
| 6 | **版本提升五处都要改** | `gui\src-tauri\tauri.conf.json`（`package.version`）+ `gui\package.json`（`version`）+ `gui\src-tauri\Cargo.toml`（`version`）+ `README.md` 徽章 + `gui\src-tauri\Cargo.lock`（`name="mcnp-ui"` 的 `version`）同步改；release 时代以 `tauri.conf.json` 为准，此处保持各处一致（**v1.6.4 曾漏 Cargo.toml，停在 1.6.3**；**v1.7.2 起纳入 Cargo.lock**）。 |
| 7 | **tauri build 增量编译不会刷新 target\release 里的 sidecar** | `node .\node_modules\@tauri-apps\cli\tauri.js build` 重建主 exe，但 `target\release\python.exe` + `target\release\_internal\` 可能是**陈旧旧版**（mtime 停留在上次），部署复制的就是旧 sidecar → "版本号新、后端旧"（缺本次修复）。**部署前必须 6.2 核对 mtime/大小**；不匹配则手动把 `binaries\` 的 sidecar 覆盖到 `target\release\` 再部署。 |
